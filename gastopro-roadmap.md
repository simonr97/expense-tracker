### Feature A.4 — Campo `date` propio en Expense + rango de fechas
- ✅ **US A.4.1**: Como sistema, necesito que `Expense` tenga un campo `date` propio (distinto de `createdAt`), para poder cargar gastos con fecha retroactiva sin pisar el timestamp de auditoría.
  - AC: `date DateTime @default(now())` agregado al modelo — no nullable, con default a la fecha actual si no se especifica. Migración aplicada.
  - AC: DTO de creación (`date`) opcional para el cliente, con la cadena de decoradores correcta: `@IsOptional()` + `@Type(() => Date)` (de `class-transformer`, convierte el string ISO entrante en instancia real de `Date`) + `@IsDate()` (valida que la conversión haya dado una fecha válida, no un `Invalid Date`). Requiere `transform: true` en el `ValidationPipe` global — *(nota: este flag es global, afecta la validación de todos los DTOs de la app; se verificó que no rompió los existentes)*.
  - Pendiente: agregar el campo `Fecha` (opcional) al `ExpenseForm` del frontend.
- ✅ **US A.4.2**: Como sistema, necesito exponer el rango de fechas (primer/último gasto) para que la UI pueda acotar la navegación por mes a datos reales.
  - AC: `GET /expenses/date-range` implementado vía `prisma.expense.aggregate({ _min: { date: true }, _max: { date: true } })`, con el resultado remapeado a una forma propia (`{ min, max }`) en vez de exponer la forma cruda `_min`/`_max` de Prisma. Probado con `curl` contra Neon.
  - AC: Tipo `ExpenseDateRange` en frontend honesto respecto al wire format — `min`/`max` tipados `string | null` (JSON no tiene tipo fecha nativo, viaja como string), contemplando el caso de tabla vacía (`null`).

### Feature A.6 — Manejo de errores en la API *(agregada 2026-10-08)*
- ✅ **US A.6.1** *(cerrada el 2026-10-14 con pruebas parciales; recibe el AC de 409 de A.5.5)*: Como sistema, necesito un filtro de excepciones global de NestJS que traduzca los errores conocidos de Prisma a respuestas HTTP correctas, en lugar de responder 500 genérico.
  - AC: `P2002` (violación de unicidad, por ejemplo un nombre repetido en `Category`, `Account` o `Merchant`) responde **409 Conflict** con un mensaje claro.
  - AC: Se evalúan también `P2025` (registro no encontrado, para los futuros `PATCH`/`DELETE`, respondería 404) y `P2003` (violación de clave foránea, por ejemplo borrar un comercio con gastos asociados, respondería 409).
  - AC: Registrado una sola vez de forma global, de modo que aplique a todos los módulos sin repetir `try/catch` en cada servicio.
  - Origen: al probar `POST /merchants` con un nombre repetido, la API respondió 500.
  - Decisiones (2026-10-13): (1) filtro registrado con `APP_FILTER` en `AppModule` (permite inyectar dependencias, a diferencia de `useGlobalFilters`); (2) en Prisma 7 con `PrismaPg` el `meta` de `P2002` **no trae `target`**: trae `modelName` y `driverAdapterError.cause.constraint.index` (por ejemplo `Merchant_name_key`); (3) el 409 sale siempre que el código sea `P2002`; el mensaje tiene dos niveles: base con `modelName`, y el campo solo si el nombre de la restricción coincide con `<Modelo>_<campo>_key` con un único campo (lectura defensiva, sin romper si falta algún nivel); (4) el cliente nunca recibe nombre de índice, mensaje de Postgres ni stack; (5) se loguea el error original en el servidor con el `Logger`; (6) códigos no manejados se delegan al comportamiento por defecto de Nest (500); (7) respuesta con `statusCode: 409`, `message` como **string** y `error: 'Conflict'`.
  - Decisión (2026-10-13): **contrato de error** para errores controlados del backend: `{ statusCode, error, code, message, details? }`. `code` es un identificador estable en mayúsculas (para este caso `RESOURCE_ALREADY_EXISTS`); `details` lleva `{ resource, field? }`; `message` es un texto para desarrolladores y respaldo, no para mostrar. El **texto amigable lo decide el frontend** mapeando `code` + `details` en un solo lugar (componente de errores de F.1.2). Logging: el filtro registra el error original en el servidor con el `Logger`: `warn` para errores esperados del cliente (409), `error` con stack solo para 5xx inesperados; nada de eso viaja al cliente.
  - Decisión (2026-10-13): alcance ampliado de A.6.1 a `P2002`, `P2025`, `P2003` y `P2000`, con **dos filtros**: un catch-all (conserva el cuerpo de las `HttpException`; errores desconocidos → 500 genérico con log `error`) y uno específico de Prisma (`P2xxx`), registrados con `APP_FILTER` con el catch-all declarado primero. Los `P1xxx` (inicialización) caen en el catch-all como 500 por ahora. Los códigos se resuelven con una **tabla indexada por el código de Prisma**:

| Prisma | HTTP | `code` del contrato | `message` base (desarrollador) |
|---|---|---|---|
| `P2002` | 409 | `RESOURCE_ALREADY_EXISTS` | A record with the same unique value already exists |
| `P2025` | 404 | `RESOURCE_NOT_FOUND` | The requested record was not found |
| `P2003` | 409 | `RELATED_RESOURCE_CONFLICT` | The operation conflicts with a related record |
| `P2000` | 400 | `VALUE_TOO_LONG` | A provided value exceeds the allowed length |

  - Notas: `P2003` no distingue "borrar algo en uso" de "referenciar algo inexistente"; se acepta 409 para ambos. `P2025` se podrá probar recién en C.3 (`PATCH`/`DELETE`). Usar el enum `HttpStatus` y derivar el texto de `error` del estado.
  - Avance (2026-10-13): implementados `CatchEverythingFilter` (catch-all) y `PrismaErrorCatch` (`P2002`, `P2025`, `P2003`, `P2000`), tipo común `ApiErrorResponse`, tabla `prismaErrors` con `satisfies` y `Object.hasOwn` para la pertenencia. `details` lleva solo `resource` (de `meta.modelName`) y `field` (deducido del índice, que nunca sale al cliente); log `warn` para los códigos mapeados y `error` con stack para los no mapeados o desconocidos. Probado `P2002` en `POST /merchants`. **Pendiente:** probar el catch-all (400 de validación, ruta inexistente 404, error forzado → 500 genérico) y confirmar el orden de registro en `AppModule` (catch-all primero).
  - Cierre (2026-10-14): `getUniqueField` ahora omite `field` si el índice es compuesto. Verificado: `P2002` en `POST /merchants` (409 con `details`), y el catch-all con `HttpException` 400, 404, 409 y 500 (formato del contrato). Orden en `AppModule`: catch-all primero, Prisma después. Decisión aceptada: conviven `INTERNAL_SERVER_ERROR` (de `HttpException` 500) e `INTERNAL_ERROR` (error desconocido y código de Prisma no mapeado), y `NOT_FOUND` / `RESOURCE_NOT_FOUND`; el mapeo del frontend debe cubrir ambos.
  - **Sin probar (anotado a propósito):** (1) el 400 de `ValidationPipe` con lista (`VALIDATION_FAILED` + `details.errors`); (2) un error que no es `HttpException` (500 genérico + stack en el log); (3) el 409 de Prisma con los dos filtros registrados a la vez. Probar cuando haya tiempo, o al construir F.1.2.
  - Pendiente: alinear versiones de Prisma (`@prisma/client`, `prisma`, `@prisma/adapter-pg`) y repetir la prueba del 409 como control.
  - **Cambio de contrato (decidido por el usuario, 2026-10-13):** los 400 de `ValidationPipe` ahora se responden con `code: 'VALIDATION_FAILED'`, `message` string fijo (`The request contains invalid fields`) y la lista en `details.errors: string[]`. Por eso `message` es siempre un string: el tipo `ErrorMessage` del frontend (`message: string[]`) debe actualizarse (afecta F.1.2) y `ApiErrorResponse.details` debe incluir `errors?: string[]`.
  - Mejora pendiente (menor): `getUniqueField` devuelve `userId_name` para un índice compuesto; omitir `field` si lo extraído contiene `_`.
  - Consecuencia en el frontend: los 400 de `ValidationPipe` traen `message` como array y el 409 como string; (reemplazado por el cambio de contrato de arriba: `message` pasa a ser siempre string; F.1.2 debe actualizar `ErrorMessage` y contemplar `details.errors`).
  - Deuda detectada: versiones de Prisma desalineadas (`@prisma/client` 7.8.0, `prisma` ^7.8.0, `@prisma/adapter-pg` ^7.10.0); alinear tras esta US.
  - Pendiente relacionado (ver "On the horizon"): mostrar estos errores en la UI, hoy solo hay `console.error`.

## EPIC O — Autenticación y aislamiento de datos *(agregada 2026-11-14; parte de Alpha 1.0)*

**Contexto:** la alfa se prueba con conocidos del usuario; sin login y sin aislamiento, todos verían los datos de todos. **Decisión del usuario (2026-11-14): el inicio de sesión es con Google** (sin contraseñas propias: no hay hash, recuperación de contraseña ni límite de intentos que construir). Reemplaza a la Feature I.1.

**Regla de seguridad central:** el `userId` sale **siempre de la sesión verificada en el servidor**, nunca del cuerpo ni de la URL, y **toda consulta** lleva ese filtro. Si falta en un solo lugar, un usuario puede leer o borrar datos de otro cambiando un `id` (IDOR). Se prueba el aislamiento a propósito.

**Línea base de seguridad para la alfa (2026-11-14; el usuario pidió "una seguridad decente"):** (1) verificar bien el token de Google en el servidor y usar el `sub` como identidad; (2) sesión en cookie `httpOnly; Secure; SameSite=Lax`, vencimiento corto y cierre de sesión que la invalide (sugerida, **decisión abierta**: cookie contra token en el navegador); (3) `userId` siempre de la sesión y filtro por usuario en toda consulta, con pruebas de aislamiento; (4) lista de emails permitidos durante la alfa; (5) solo HTTPS y CORS limitado al origen del frontend; (6) cabeceras de seguridad (`helmet`) y límite de peticiones (`@nestjs/throttler`); (7) secretos solo en variables de entorno, nunca en el repositorio ni en los logs (tampoco tokens ni cookies); (8) validación de entrada (ya hay `whitelist: true`) y dependencias al día; (9) copias de seguridad de la base (a confirmar con el plan de Neon). **Dónde viven el frontend y la API: sin decidir.** Condiciona la cookie: con un solo sitio para el navegador (frontend en Vercel con reenvío de `/api/*` al backend, o ambos en Vercel) la cookie es simple; con dominios distintos es cookie de terceros y se complica (se arregla con un dominio propio y subdominios). Hasta decidir, dominio, banderas de la cookie y origen permitido van como variables de entorno, no escritos en el código.

**Decisión de sesión (2026-11-18, del usuario): la sesión se guarda en la base y viaja en una cookie `httpOnly; Secure; SameSite=Lax` con un identificador aleatorio** (no un token firmado que lleve los datos), porque quiere que los cambios (cerrar una sesión, bloquear, quitar acceso) tengan **efecto inmediato** y no esperen a un vencimiento. Diseño: identificador largo y generado con criptografía por el servidor; en la base se guarda su **hash** (no el valor en claro); tabla de sesiones con `userId`, creación, vencimiento absoluto y última actividad (actualizar la última actividad solo cada cierto rato para no escribir en cada petición); cerrar sesión borra la fila y "cerrar todas" borra las del usuario. Costo asumido: una consulta a la base por petición (con la base de Neon gratuita, la primera tras inactividad es más lenta; índice sobre el identificador y conexión con pool). Repaso del 2026-11-18: dos tokens distintos: el de Google (una sola vez, prueba quién es la persona) y la sesión propia; verificar el token de Google evita que alguien mande uno inventado (firma, destinatario y vencimiento) y es un paso **distinto** de la lista de permitidos (primero se verifica, después se decide si puede entrar). Calificación del repaso: borrar inexistente (404 contra 400): débil; defecto de `'es'`: débil; cookie contra token: débil (corregido); para qué sirve cada token y por qué verificar: parcial.

**Plan de trabajo con identidad simulada (2026-11-18, propuesta del usuario):** construir el aislamiento contra un usuario simulado y enchufar el login real al final. Orden: (1) tabla de usuarios y `userId` nullable en todas las tablas; (2) usuarios sembrados en la base: el del usuario (con su email y el `sub` vacío) y un segundo falso para pruebas; (3) relleno de los datos actuales con el usuario sembrado y recién después NOT NULL (**el relleno va antes de activar el filtro por `userId`**, porque las filas con `userId` nulo dejan de verse; y no se abre la app a otros hasta que termine); (4) guard y decorador `@CurrentUser()` que devuelven el usuario sembrado, y filtro por `userId` en todas las consultas (el resto del código nunca pregunta "¿quién es?"); (5) pruebas de aislamiento con los dos usuarios (O.3.2, sin depender de Google); (6) login real con Google: solo cambia lo que devuelve el guard; en el primer ingreso se vincula la fila sembrada por email, **solo si Google confirma `email_verified`**, y se guarda el `sub`. **Riesgo: el bypass de autenticación no debe llegar a producción:** se activa solo con una variable de entorno explícita y fuera de producción; si falta cualquiera de las dos condiciones o no se conoce el entorno, el servidor no arranca (falla cerrado); nunca es el valor por defecto; una prueba automática verifica que en producción no se puede activar. ## Decisiones diferidas (revisitar después de Alpha 1.0) *(2026-10-20)*

Contexto: al diseñar el modelo de datos la conversación se fue ramificando. Decisión del usuario (2026-10-20): **primero ver si alguien quiere usar la aplicación; la lógica de negocio fina se define después.** Estamos en alfa y todo es susceptible a cambios. Lo que sí se mantiene para Alpha 1.0: Income (Epic M), tabla `PaymentMethod` creada libremente por el usuario con "Cash" como valor por defecto, y monedas ARS y USD.

Para revisitar:
- **Jerarquía de cuentas.** Idea del usuario: una entidad bancaria con varias subcuentas (cuenta sueldo, caja de ahorro, cuenta de crédito). Modelo propuesto: `Institution` (Santander, Mercado Pago, Cash) → `Account` (subcuenta) → ¿método de pago?. Hoy `Account` es plana (solo nombre) y hace de institución.
  - Qué hacer con las cuentas ya creadas: convertirlas en `Institution` con una `Account` por defecto, o dejarlas como cuentas y crear instituciones aparte.
  - Experiencia: el formulario de gasto mostraría una lista única con institución y cuenta juntas ("Santander · Cuenta sueldo (ARS)"); crear una cuenta exige elegir o crear su institución (más trabajo que el quick-create actual de solo nombre).
- **Dónde vive la moneda.** (a) en cada movimiento (decidido el 2026-10-18, vigente), (b) en la cuenta ("Santander ARS", "Santander USD"; encaja con cómo piensa el usuario y simplifica los balances por cuenta), (c) en el método de pago. Argumento del usuario: quiere saber cuántos pesos y cuántos dólares tiene en total, no un total mezclado. Pregunta para decidir: ¿gastos con tarjeta en dólares pagados desde una cuenta en pesos?
- **¿El método de pago es entidad o tipo fijo?** Con subcuentas, "cuenta de crédito" y "caja de ahorro" ya serían cuentas distintas; el método podría reducirse a un tipo (débito, crédito, transferencia, efectivo). Hace falta entidad solo si se registra cada tarjeta.
- **Efectivo.** Decidido y luego diferido: cuenta especial "Cash" con método "Cash" autoseleccionado y bloqueado. Ahora "Cash" es solo un método por defecto y el gasto en efectivo no necesita cuenta (`accountId` opcional, 2026-10-20).
- **Reglas que dependen de la cuenta** (diferidas): filtrar los métodos de pago según la cuenta elegida y validar en el servidor que el método pertenezca a la cuenta (el usuario razonó bien la necesidad: dos sesiones abiertas, interfaz desactualizada).
- **Formulario más rico para crear cuentas** (nombre + métodos, de forma atómica), diferido junto con la jerarquía.
- **Ingresos:** si "de dónde viene" es un campo propio o va en la descripción; tab con control por cuenta (Epic E).
- **Totales por moneda en el tab Income:** idea del usuario de una card con el total en pesos y otro en dólares.
- **Internacionalización (i18n) y cambio de idioma de la interfaz a español** *(2026-11-13; ideas a decidir a futuro, **no son tareas todavía**)*: la alfa se probará sobre todo con conocidos del usuario, mayormente argentinos, así que cambiar la interfaz de inglés a español es un posible cambio; y usar i18n (con claves de traducción) es un posible recurso, con un menú de settings para elegir español o inglés. Notas de la consulta del 2026-11-13, para cuando se decida: estimación a ojo de 3 a 5 días de trabajo; lo más caro es extraer todos los textos (el costo es el mismo traduciendo solo a español); si se hace, conviene extraer una sola vez con claves y dejar el selector como extra; `@angular/localize` resuelve el idioma al compilar (un build por idioma) y no sirve para cambiarlo en tiempo de ejecución, para eso hace falta una librería de tiempo de ejecución (por ejemplo Transloco) o un servicio propio con señales; los estados (`Completed`, `Pending`) son valores que viajan al backend, solo se traduce la etiqueta; los errores del servidor se traducirían por el `code` estable de `toUiError`; el español es ~20-30 % más largo y puede apretar botones, pills y columnas; el `<input type="date">` nativo usa el idioma del navegador. Hasta que se decida, la interfaz sigue en inglés y los montos usan `'es-AR'`.
- **Comparación de gastos (Feature C.4, C.4.1 y C.4.2)** *(2026-11-09)*: sale de Alpha 1.0 por decisión del usuario. Se revisita después de la alfa, con el servicio de permisos del plan (H.3). El diseño y los AC quedan como están en la Feature C.4. Sin impacto en C.2.1: el panel de detalle solo no tiene el botón "Comparar"; `ExpenseDetail` sigue siendo reutilizable con cualquier gasto.
